# Adding peculiar-rpc to a product

This document is written for an agent that has been asked to add
peculiar-rpc to a product: to give a Haskell backend an API that native gRPC,
gRPC-Web, Connect and REST clients can all call. It is complete: everything
you need is here or in the repository files it names. Read it fully before
touching the product. Work through the sections in order, and finish with the
checklist at the end; you are done only when every item on it holds.

It describes peculiar-rpc 0.3.0.0.

## 1. What you are integrating

peculiar-rpc turns `.proto` files into a Haskell service and a Haskell client.

- **The contract is the `.proto` file.** Messages are generated by proto-lens.
  One Template Haskell splice then derives, per service, a server record with
  one handler field per RPC and a client record with one calling field per
  RPC. A missing handler is a missing field, a renamed RPC is a compile
  error, and a streaming handler cannot stand where a unary one is expected.
- **The service is a WAI application.** `Rpc.withServer` builds a `Server`
  value from the endpoints; `Rpc.middleware` mounts it in front of the
  product's own WAI application, and `Rpc.application` serves it alone. On
  one port it answers native gRPC, gRPC-Web and Connect (unary, GET and every
  streaming kind), the proto3 JSON mapping on all three, REST from
  `google.api.http` options, and an OpenAPI document. No proxy, no sidecar.
- **The library can also run the server.** `Rpc.serveEndpoints` and
  `Rpc.serve` add a listener with h2c sniffing, TLS by ALPN, Unix sockets,
  HTTP/2 keepalive, idle and age limits, connection caps and graceful
  shutdown, with HTTP/2 tuned for gRPC load. Use them when the product has
  no HTTP server yet, or when it serves heavy gRPC traffic.
- **The client** speaks all three protocols over HTTP/2 or HTTP/1.1, with
  deadlines, retries, compression, mutual TLS and interceptors. A program that
  only calls, such as an SDK, depends on `peculiar-rpc-client`, which carries
  no server stack.

The public API is `Peculiar.Rpc`, imported qualified as `Rpc`. For a client
alone it is `Peculiar.Rpc.Client`, under the same names.

## 2. What to ask before you start

Stop and ask if any of these is missing. Do not guess them.

1. **Which services and methods**, or the `.proto` files if they exist. If
   you are to design them, ask what each call is for and who calls it.
2. **Who the clients are**: browsers, mobile apps, other services, the
   command line. Browsers decide CORS and restrict streaming (section 9).
3. **Where the API is served**: mounted in the product's existing HTTP server
   (which one: warp, servant, scotty, Yesod), or a server of its own. Which
   host and port, and whether TLS is terminated in front of it or by the
   process.
4. **How callers authenticate**: a bearer token, an API key, mutual TLS, or
   nothing. Where the product already validates credentials.
5. **The proto package name and version**, such as `shop.v1`. It is part of
   every path and cannot change later without breaking clients.
6. **Whether reflection and OpenAPI may be public.** Both publish the schema.

## 3. Rules that are not negotiable

- **The `.proto` file is the single source of truth.** Never write a
  message type, a route or a JSON shape by hand. Generated code is never
  committed; it is built from the `.proto` files.
- **Never hand-write the routing.** `Rpc.endpoint` reads the routes and the
  Connect GET permissions from the service descriptor. Do not match paths
  like `/shop.v1.Orders/Place` in the product's own code.
- **Mount, do not wrap.** The RPC service goes in front of the product's
  application with `Rpc.middleware`, or in a `Raw` servant endpoint. Do not
  put a proxy, a second port or a sidecar in front of it for gRPC-Web or
  Connect: it speaks them already.
- **Failures are typed.** A handler that fails for a reason the caller should
  see throws `RpcError` with the right `Code`. Anything else becomes
  `UNKNOWN`, and its text leaks to the caller unless `revealErrors` is off.
- **Authentication is an interceptor**, not a check copied into every
  handler.
- **Do not break the contract.** Never renumber or reuse a field, rename an
  RPC or change a type in place. Add new fields and methods; deprecate old
  ones. Run `buf breaking` if the product has it.
- **Every unary call a client makes has a deadline.**

## 4. The flake and the package set

peculiar-rpc builds with specific releases of its HTTP stack: http2 5.4.6 with
`nix/http2-settings-window.patch`, http-semantics 0.4.1, warp 3.4.15 and wai
3.2.5, for security fixes that the releases in nixpkgs lack and a send-window
fix no http2 release carries yet. The product must build against the same
package set, or the versions will conflict. The repository exports it as
`nix/haskell-packages.nix`.

Add the flake as an input, following the product's own nixpkgs:

```nix
inputs.peculiar-rpc = {
  url = "github:peculiar-systems/peculiar-rpc/v0.3.0.0";
  inputs.nixpkgs.follows = "nixpkgs";
};
```

Build the product's Haskell packages with that package set, and take the
libraries from the flake's packages:

```nix
{ lib, pkgs, peculiar-rpc, ... }:
let
  haskellPackages = import "${peculiar-rpc}/nix/haskell-packages.nix" { inherit lib pkgs; };
  rpc = peculiar-rpc.packages.${pkgs.stdenv.hostPlatform.system};
in
haskellPackages.callPackage ./server.nix {
  peculiar-rpc = rpc.peculiar-rpc;
}
```

| Package | When to depend on it |
|---|---|
| `peculiar-rpc` | A server. Re-exports the whole client too. |
| `peculiar-rpc-client` | A program that only calls: an SDK, a CLI, a job. No warp, no wai. |
| `peculiar-rpc-core` | Rarely: the wire formats as pure values. |
| `peculiar-rpc-json` | Rarely: the proto3 JSON codec on its own. |
| `peculiar-rpc-apis` | `google.api`, `google.rpc` and `buf.validate` messages, for protos that import them. |

A server also needs `wai` and `warp` for its own application, and
`proto-lens-runtime` for the generated code.

**Generated code.** Run `protoc` with `proto-lens-protoc` in a derivation,
listing the `.proto` files by name (a glob over a store path is
import-from-derivation), and compile the output as its own library with
plain `GHC2021`, since generated code is not written for a project's
extensions. Protos that import `google/api/annotations.proto` or
`buf/validate/validate.proto` get those from `peculiar-rpc-apis`.

**Runtime.** Link the server with
`-threaded -rtsopts "-with-rtsopts=-N -A64m"`. The HTTP/2 stack needs the
threaded runtime, and the larger allocation area cuts collection time under
load.

## 5. Deriving a service

```haskell
{-# LANGUAGE TemplateHaskell #-}

module Shop.Orders (orders) where

import Peculiar.Rpc qualified as Rpc
import Proto.Shop.V1.Orders

Rpc.deriveService ''Orders

orders :: Env -> OrdersServer
orders env = OrdersServer{place = place env, watch = watch env}
```

`deriveService` writes `OrdersServer` and `OrdersClient`; `deriveServer` and
`deriveClient` write one each. Field names are the method names, so the module
needs `DuplicateRecordFields` and `NoFieldSelectors`.

| Kind | Server field | Client field |
|---|---|---|
| Unary | `Context -> i -> IO o` | `i -> IO o` |
| Server stream | `Context -> i -> (o -> IO ()) -> IO ()` | `i -> (o -> IO ()) -> IO ()` |
| Client stream | `Context -> IO (Maybe i) -> IO o` | `((i -> IO ()) -> IO ()) -> IO o` |
| Bidi stream | `Context -> IO (Maybe i) -> (o -> IO ()) -> IO ()` | `((i -> IO ()) -> IO ()) -> (o -> IO ()) -> IO ()` |

Handlers take the product's environment as an argument and declare what they
touch with its capability classes, as the rest of the product does. The
`Context` carries the request metadata (`Rpc.lookupHeader "name"
context.metadata`), the caller's timeout, the peer address, the method path,
and `respondWith` and `trailWith` for response headers and trailers.

Mark read-only methods `option idempotency_level = NO_SIDE_EFFECTS;` in the
`.proto` file: they then accept Connect GET, which browsers and CDNs can
cache.

## 6. Errors

```haskell
Rpc.throwRpc Rpc.NotFound "no order with that id"
throwIO (Rpc.withMetadata (Rpc.pushback (Rpc.seconds 2)) (Rpc.rpcError Rpc.Unavailable "try again shortly"))
```

- Pick the code by what the caller should do: `InvalidArgument` for a bad
  request, `NotFound`, `AlreadyExists`, `FailedPrecondition` for a state
  that forbids the call, `PermissionDenied` and `Unauthenticated`,
  `ResourceExhausted` for limits, `Unavailable` only for failures a retry
  can fix.
- An `RpcError` reaches every protocol as the same code, message,
  `google.rpc.Status` details and trailers: a Connect error body, gRPC
  trailers, a REST status.
- Any other exception is `UNKNOWN` and goes to `Calls.report`. Set
  `revealErrors = False` in production so its text stays in the log.
- Requests are validated against protovalidate rules in the `.proto` file
  before the handler runs; a violation is `INVALID_ARGUMENT` naming each
  field. Put input rules there, not in handlers.

## 7. Mounting it beside the product's routes

This is the default. The product keeps its HTTP server and its routes; the RPC
service answers its own paths in front of them.

```haskell
import Network.Wai.Handler.Warp qualified as Warp
import Peculiar.Rpc qualified as Rpc

main :: IO ()
main = withEnv \env ->
  Rpc.withServer calls [Rpc.endpoint (orders env), Rpc.health env.statuses] \rpc ->
    Warp.runSettings settings (Rpc.middleware rpc (productApp env))
 where
  calls = Rpc.defaultCalls{Rpc.interceptor = authenticated, Rpc.revealErrors = False}
```

- `Rpc.withServer :: Calls -> [Endpoint] -> (Server -> IO a) -> IO a`
  builds the value. Build it once, at start, and keep it for the life of the
  process.
- `Rpc.middleware rpc app` answers the RPC paths, the REST paths the
  services' `google.api.http` options declare, their CORS preflights and
  `/openapi.json` when `openApi` is set, and passes every other request to
  `app`. RPC paths win over any route in `app`.
- `Rpc.application rpc` answers everything itself: an unknown path is
  `UNIMPLEMENTED` in the caller's protocol.
- **servant**: end the API with `Raw`, served by
  `Tagged (Rpc.application rpc)`, or wrap the served application in
  `Rpc.middleware rpc`. The RPC paths must stay at the root: gRPC clients
  cannot call under a prefix.
- **scotty, Yesod and others**: wrap their WAI application in
  `Rpc.middleware rpc`.

`Calls` holds everything about calls:

| Field | Default | Set it when |
|---|---|---|
| `interceptor` | none | Always, for authentication, metrics and logging. |
| `revealErrors` | `True` | Production: set `False`. |
| `report` | stderr | Always: send it to the product's journal. |
| `cors` | `Nothing` | Browsers on another origin call the API. |
| `receiveLimit` | none | Always: the largest request message the product accepts. |
| `headerLimit` | 16 KiB | Rarely. |
| `openApi` | `Nothing` | REST clients need a document. |

Native gRPC works through WAI: the service hands its trailers to warp's
HTTP/2 through the request's `HTTP2Data`. Warp serves HTTP/2 over TLS with
`warp-tls`, and over plaintext to clients that open with the HTTP/2 preface.
Warp's HTTP/2 runs with the http2 package's default rate limits, which a
heavily loaded grpc-go client can exceed; if the product expects that load,
serve it with section 8 instead.

## 8. Serving it alone

When the product has no HTTP server, or needs the gRPC-tuned listener:

```haskell
main :: IO ()
main = withEnv \env ->
  Rpc.serveEndpoints
    Rpc.defaultSettings
      { Rpc.host = "0.0.0.0"
      , Rpc.port = 8080
      , Rpc.calls = calls
      , Rpc.beside = Just (productApp env)
      }
    [Rpc.endpoint (orders env)]
```

`serveEndpoints` is `withServer` and `middleware` over
`Rpc.serve :: Settings -> Wai.Application -> IO ()`, which serves any WAI
application; `beside` is the product's application, and `Nothing` answers
RPC alone. `Settings` adds `tls` (`Rpc.tlsFromFiles`, reloaded per
connection; `Rpc.requireClients` for mutual TLS), `unixSocket`, `keepalive`,
`idleTimeout`, `maxAge`, `maxConnections`, `http2` and `grace`. It returns
after SIGTERM or SIGINT, once running requests have drained for up to
`grace`; new calls meanwhile get `UNAVAILABLE`, so clients with retries go
elsewhere. Pass `stopWhen` to stop on something else.

Behind a TLS terminator, point it at the plaintext port; for native gRPC the
terminator must speak HTTP/2 to the backend.

## 9. Authentication and browsers

```haskell
authenticated :: Rpc.Interceptor
authenticated = Rpc.Interceptor \route context continue ->
  case Rpc.lookupHeader "authorization" context.metadata of
    Just token | valid token -> continue context
    _ | route.service == "grpc.health.v1.Health" -> continue context
    _ -> Rpc.throwRpc Rpc.Unauthenticated "sign in first"
```

An interceptor sees every call with its route and `Context`, health and
reflection included. It can refuse with an `RpcError`, pass a changed
`Context`, time or log the call. Interceptors compose with `<>`, the left one
outermost. When the check needs the product's environment, write a function
from the environment to an `Interceptor`.

For browsers:

- Set `cors`: `Just Rpc.permissive` in development, `Rpc.Cors{origins =
  Rpc.OnlyOrigins [...], ...}` in production. Without it a browser on another
  origin cannot read a single status.
- A browser can only make unary and server-streaming calls. Add
  `Rpc.BrowserReachable Orders` to a signature to make any other kind a type
  error that names the method.
- Browser clients use gRPC-Web or Connect: in TypeScript,
  `@connectrpc/connect-web` with `createGrpcWebTransport` or
  `createConnectTransport`; in Dart, `GrpcOrGrpcWebClientChannel`.

## 10. Health, reflection, REST

- `Rpc.health statuses` serves `grpc.health.v1`, with `Rpc.newStatuses` and
  `Rpc.setServing`. Add it to every server; orchestrators probe it.
- `Rpc.withReflection endpoints` serves `grpc.reflection` so `grpcurl` works
  without the `.proto` files. It publishes the schema: add it only where the
  owner allowed (section 2).
- A method annotated with `google.api.http` is also served at its REST path
  as JSON, with nothing to register. Set `openApi` to serve its OpenAPI 3.1
  document at `/openapi.json`, or print it without a server with
  `peculiar-rpc-openapi`.

## 11. Calling it

```haskell
Rpc.withConnection (Rpc.Secure Rpc.systemTls) "api.example.org" 443 \connection -> do
  let orders = Rpc.client options (Rpc.Http2 connection Rpc.Grpc) :: OrdersClient
      options = Rpc.defaultOptions{Rpc.deadline = Just (Rpc.seconds 5), Rpc.requestMetadata = Rpc.header "authorization" token}
  placed <- orders.place request
  ...
```

One connection carries any number of concurrent calls and reopens when the
server closes it; open it once and share it. `Rpc.defaultRetry` retries
`UNAVAILABLE` within the call's deadline. Over HTTP/1.1, use
`Rpc.web manager Rpc.Connect url` and `Rpc.Http1`.

## 12. Testing with the derived client

Test the service through the derived client, over the real protocols, not by
calling handlers directly: the client is derived from the same splice, so a
test cannot drift from the contract.

```haskell
withService :: Env -> (Int -> IO a) -> IO a
withService env use =
  Rpc.withServer Rpc.defaultCalls{Rpc.report = const (pure ())} [Rpc.endpoint (orders env)] \rpc ->
    Warp.testWithApplication (pure (Rpc.middleware rpc (productApp env))) use

placesAnOrder :: Property
placesAnOrder = withTests 1 . property $ do
  env <- liftIO fakeEnv
  placed <- liftIO $ withService env \port ->
    Rpc.withConnection Rpc.Plaintext "127.0.0.1" port \connection ->
      (Rpc.client Rpc.defaultOptions (Rpc.Http2 connection Rpc.Grpc) :: OrdersClient).place request
  placed ^. #status === "accepted"
```

- Build the environment from fakes of the same capability records; no mocking
  library.
- Cover each protocol the product's clients use: `Rpc.Grpc` and
  `Rpc.Connect` over `Rpc.Http2`, and `Rpc.Http1` with `Rpc.web` for Connect
  and gRPC-Web as browsers send them.
- Assert failures by code: `try @Rpc.RpcError` and compare
  `failure.status.code`.
- To test the listener itself, run `Rpc.serveEndpoints` with `port = 0`,
  `onListening` to learn the port, and `stopWhen` to end it.

## 13. Pitfalls

- Building against the nixpkgs http2 or warp. Use the package set from
  section 4.
- Mounting the service under a path prefix. gRPC paths live at the root.
- Putting the product's catch-all route in front of `Rpc.middleware`. The
  middleware goes outermost.
- Opening a client connection per call.
- A unary call without a deadline.
- Returning `UNKNOWN` by throwing ordinary exceptions for expected failures.
- Client or bidi streaming methods meant for browsers.
- Leaving `revealErrors` on in production, or reflection on where the owner
  did not want it.
- Forgetting `-threaded`.

## 14. Done checklist

You are finished only when every line holds.

- [ ] The services, clients, host, authentication, package name and
      reflection policy came from the product's owner, not from you.
- [ ] The `.proto` files are the only definition of messages and routes;
      generated code is built, not committed.
- [ ] The product builds with peculiar-rpc's package set and links with
      `-threaded`.
- [ ] Each service is derived with `deriveService` or `deriveServer`, and
      every handler takes the product's environment.
- [ ] The service is mounted with `Rpc.middleware` in front of the
      product's application, or served with `Rpc.serveEndpoints`, on one
      port.
- [ ] `Calls` sets an interceptor for authentication, a `report` to the
      product's journal, a `receiveLimit`, and `revealErrors = False` in
      production.
- [ ] CORS is set if browsers call from another origin, and browser-facing
      services carry `BrowserReachable`.
- [ ] Health is served; reflection only where allowed.
- [ ] Expected failures throw `RpcError` with a fitting code.
- [ ] Tests call every method through the derived client over each protocol
      the product's clients use, including a failure case.
- [ ] Every client call has a deadline.
